## 1. Продуктовое видение

**Проблема.** Мастер ресниц ведёт записи в Instagram Direct, мессенджерах и бумажных тетрадях: двойные записи, забытые клиенты, no-show, потерянные формулы (какие ресницы, изгиб, длина были в прошлый раз), нет напоминаний и предоплаты.

**Решение.** Независимое приложение: мастер получает календарь, каталог услуг, карточки клиентов с lash-специфичными данными, персональную ссылку для записи, напоминания и предоплату. Клиент записывается за минуту без звонков и переписки.

**Отличие от Booksy [Мы].**
1. Специализация: lash-сценарии «из коробки» (наращивание → коррекции через 2–3 недели, цена коррекции зависит от срока, формула ресниц, патч-тест, аллергии, снятие).
2. Персональная ссылка мастера для Instagram/TikTok/Telegram — запись без установки приложения (см. 20, решение Q3).
3. EU-first: GDPR, PL/EN/RU/UK, BLIK/Przelewy24, Apple Pay, польские реалии (часовой пояс Europe/Warsaw, PLN, SMS-провайдеры Польши).
4. Чистая архитектура под общий backend: Android позже без переписывания бизнес-логики на сервере.

**Метрики успеха MVP.**
- Мастер: время от установки до первой принятой записи ≤ 15 минут.
- Клиент: запись за ≤ 60 секунд от открытия ссылки/приложения.
- Доля no-show у мастеров с напоминаниями+депозитом ≤ половины исходной (сравнение по опросу).
- Доля записей, созданных клиентами самостоятельно, ≥ 50% через 2 месяца.
- Crash-free sessions ≥ 99,5%.

## 2. Анализ Booksy (публичная информация)

Booksy — маркетплейс + SaaS для beauty/wellness: два приложения (Booksy for Customers и Booksy Biz), онлайн-запись 24/7, календарь, клиентская база, напоминания, платежи и no-show защита, маркетинг, отчёты.

### 2.1. Регистрация клиента и мастера
- **Клиент [Booksy]:** аккаунт в customer-приложении; профиль с настройками уведомлений, записями, отзывами, платёжными методами; можно записывать членов семьи и питомцев.
- **Мастер/бизнес [Booksy]:** регистрация в Booksy Biz, создание бизнес-профиля, добавление сотрудников. Точные шаги онбординга в открытых материалах подробно не описаны — не подтверждено.
- **[Мы]:** быстрый вход (Sign in with Apple, Google, email/телефон + одноразовый код), гостевая запись по ссылке с подтверждением телефона, мастеру — онбординг-мастер из 5 шагов (см. 8.2).

### 2.2. Профиль салона/мастера
- **[Booksy]:** бизнес-профиль на маркетплейсе; на вкладке Details видна «Payment & Cancellation Policy»; у сотрудников профили с назначением услуг.
- **[Мы]:** профиль мастера/салона: имя, био, адрес и карта, часы работы, контакты, соцсети, политика отмены, портфолио, отзывы, список услуг, команда.

### 2.3. Каталог услуг и цены
- **[Booksy]:** настраиваемые услуги: разрешить самозапись (self-booking), интервалы начала записи (например, каждые 30 мин), padding time (буфер до/после), processing time (мастер свободен в период «обработки»), parallel clients, мобильные услуги, кастомные вопросы клиенту при записи, сообщение перед визитом, разные варианты/цены услуги для разных сотрудников, no-show защита на уровне услуги.
- **[Мы]:** категории → услуги → варианты (длительность, цена, тип цены: фиксированная / «от»), буфер после, разные цены и длительность для разных мастеров. Lash-шаблоны (V1 каталога): Classic, 2D, 3D, Volume, Mega Volume, Hybrid, Lash Lift, Коррекция 2–3 нед., Снятие.

### 2.4. Выбор услуги
- **[Booksy]:** клиент выбирает одну или несколько услуг в профиле.
- **[Мы]:** MVP — одна основная услуга + опциональные добавки (add-ons: снятие чужих ресниц, ламинирование бровей и т.п.); V2 — корзина из нескольких услуг с общей цепочкой времени.

### 2.5. Выбор мастера
- **[Booksy]:** в бизнесе с командой клиент выбирает конкретного сотрудника (или «любого» — подробности не подтверждены).
- **[Мы]:** MVP — выбор конкретного мастера; V2 — «любой свободный» с балансировкой нагрузки.

### 2.6. Выбор даты и свободного времени
- **[Booksy]:** клиент видит доступность и записывается сам; владелец настраивает шаг начала записи.
- **[Мы]:** серверный расчёт слотов (раздел 12), учёт минимального времени до записи, максимального горизонта, буфера, перерывов и заблокированного времени.

### 2.7. Создание, перенос, отмена
- **[Booksy]:** клиент может отменять и переносить в приложении; владелец может ограничить окно переноса (Advanced Options → Booking Settings); перенос в customer-приложении технически означает отмену первой записи и создание новой, возможны сборы; поддержка Booksy не переносит записи за клиента; владелец получает уведомления об изменениях.
- **[Мы]:** перенос — операция над той же записью с историей изменений (сохраняем депозит и связь платежей); политика — по окну до визита (раздел 13).

### 2.8. Календарь мастера
- **[Booksy]:** кастомизируемый календарь с цветовой кодировкой и drag-and-drop, тайм-офф, календари сотрудников, права на просмотр чужих календарей.
- **[Мы]:** день/неделя, drag-and-drop переноса, цвета по услугам/статусам, быстрые действия (блок времени, запись клиента).

### 2.9. Рабочие часы, перерывы, блокировки
- **[Booksy]:** шифты сотрудников (редактируются индивидуально), time-off, padding.
- **[Мы]:** недельный график с несколькими интервалами в день, исключения по датам, перерывы, блокировки (разовые и повторяющиеся), отпуск.

### 2.10. Карточка клиента и история
- **[Booksy]:** карточка: история, будущие записи, контакты, заметки, фото, теги/фильтры, кастомные формы согласия и вейверы, объединение дублей.
- **[Мы]:** то же + **lash-профиль клиента** (формула ресниц, аллергии, патч-тест) — раздел 10.

### 2.11. Напоминания
- **[Booksy]:** автоматические напоминания и подтверждения; бесплатные SMS-напоминания (по заявлению Booksy сокращают no-show вдвое); email/SMS рассылки клиентской базе.
- **[Мы]:** push (основной) → SMS (fallback/по выбору) → email (чеки, документы); схема — раздел 14.

### 2.12. Депозит и предоплата
- **[Booksy]:** депозит — предоплата части/всей стоимости при записи, вычитается из итогового чека, удерживается при неявке; настраивается по услугам, требует включённых мобильных платежей.
- **[Мы]:** MVP — депозит (фикс/процент) по услуге через Stripe; см. раздел 15.

### 2.13. Политика отмены и no-show
- **[Booksy]:** cancellation fee — карта клиента сохраняется и проверяется при записи, комиссию можно списать автоматически или простить вручную; No-Show Protection настраивается на уровне услуги: процент, срок бесплатной отмены, авто/ручное списание; выплаты — на следующий рабочий день или ускоренно.
- **[Мы]:** MVP — политика «окно бесплатной отмены» + удержание депозита; V2 — card-on-file и авто-списание сбора.

### 2.14. Повторная запись
- **[Booksy]:** «быстрая перезапись в 2 клика» из прошлого визита.
- **[Мы]:** кнопка «Записаться снова» + для ресниц — умное предложение даты коррекции через N дней (раздел 9.3).

### 2.15. Лист ожидания
- **[Booksy]:** клиент встаёт в лист на конкретные даты; при освобождении слота (отмена/расширение часов) автоматически уходит SMS со ссылкой; кто первый — тот записался; автозапись не выполняется; владелец видит лист в календаре и может использовать его для оценки спроса.
- **[Мы]:** V2 (см. 9.5).

### 2.16. Портфолио работ
- **[Booksy]:** фото на бизнес-профиле и в клиентских карточках (фото клиента). Отдельная витрина портфолио в открытых материалах для customer-приложения не подтверждена.
- **[Мы]:** MVP — галерея работ на профиле мастера (с тегами услуг); V2 — фото «до/после» в карточке клиента с согласием.

### 2.17. Отзывы
- **[Booksy]:** отзывы в приложении клиента (раздел профиля клиента). Условия публикации (только после визита) и ответы владельца в открытых материалах не подтверждены; принято считать стандартом маркетплейса.
- **[Мы]:** отзыв только после завершённой записи (verified visit), ответ мастера, модерация жалоб. MVP — базовые; V2 — ответы/жалобы/сортировки.

### 2.18. Несколько мастеров
- **[Booksy]:** профили сотрудников, услуги по сотрудникам, шифты, комиссии, ресурсы.
- **[Мы]:** MVP — один салон, до N мастеров (ограничение по тарифу); V2 — комиссии, ресурсы (кровати/кабинеты).

### 2.19. Роли
- **[Booksy]:** 5 уровней: Owner, Manager (полный доступ), Reception (управляет записями всех, без финансов и смен), Staffer (свой календарь и клиентская база), Basic Staffer (только свой календарь). Доступ к календарям и клиентской базе настраивается.
- **[Мы]:** Owner / Manager / Reception / Employee / Customer; MVP — Owner, Employee, Customer (раздел 17).

### 2.20. Статистика и доход
- **[Booksy]:** отчёты по продажам и выручке, эффективность сотрудников, учёт кассы, комиссии.
- **[Мы]:** MVP — доход, число визитов, средний чек, no-show; V2 — заполняемость, retention, комиссии сотрудников (раздел 16).

### 2.21. Прочее у Booksy (вне нашего MVP)
Маркетплейс и его трафик, продвижение Boost (скидка на первый визит), кампании (flash sale и т.д.), подарочные карты, абонементы и пакеты, лояльность (штампы), склад, Tap to Pay/ридеры, быстрые выплаты, интеграция с соцсетями, анкеты/вейверы. Часть перенесём в V2/V3.

| Роль | Описание |

## 5. Customer journey (полный)

1. **Открытие.** Ссылка мастера (Instagram bio / Telegram / QR / визитка) → веб-страница записи или универсальная ссылка, открывающая приложение. В V2 — поиск по городу и категории.
2. **Профиль мастера.** Фото работ, услуги и цены, отзывы, адрес, политика отмены.
3. **Выбор услуги.** Например «Наращивание 2D» + опциональные добавки. Видны цена, длительность, размер депозита.
4. **Выбор мастера** (если в салоне их несколько).
5. **Выбор даты и времени.** Календарь ближайших дней; только реальные свободные слоты.
6. **Идентификация.** Вход в аккаунт или гостевое подтверждение телефона по коду. Запрос имени, телефона, email, ответов на вопросы мастера (аллергии, носите ли линзы, была ли реакция на клей).
7. **Согласия.** Политика отмены (явный чекбокс), обработка данных, отдельная необязательная галочка на маркетинг; для здоровья — явное согласие (см. 18).
8. **Оплата депозита** (если требуется): Apple Pay / карта / BLIK; страница с итогом и суммой к оплате на визите.
9. **Подтверждение.** Экран «Записаны», «Добавить в календарь», адрес и маршрут, push+email с деталями.
10. **До визита.** Напоминания (24 ч, 2 ч), возможность перенести/отменить в допустимое окно, чат/звонок мастеру (V2).
11. **Визит.** Отметка «Пришла» мастером; оплата остатка вне приложения (наличные/карта/BLIK у мастера) — MVP; онлайн-оплата остатка — V2.
12. **После визита.** Благодарность, просьба об отзыве, инструкции по уходу, предложение записаться на коррекцию.
13. **Повторная запись.** Из истории в 2 нажатия; напоминание о коррекции.
14. **Управление аккаунтом.** Язык, уведомления, экспорт и удаление данных, способы оплаты, список записей.
15. **Лист ожидания** (V2): нет слотов → «Сообщить, когда освободится».

## 6. Master / Owner journey (полный)

1. **Регистрация и онбординг:** вход → тип аккаунта (соло / салон) → профиль (имя, фото, био, город, адрес) → рабочие часы → выбор услуг из lash-шаблона и правка цен → политика отмены и депозит → подключение платежей (Stripe Connect onboarding, необязательно на первом шаге) → «Ваша ссылка для записи» (копировать/QR/поделиться в Instagram).
2. **Ежедневная работа:** экран «Сегодня» (записи, пробелы, ближайший клиент) → карточка записи → «Пришёл» → «Начать» → «Завершить» (итоговая цена, чаевые, заметки, формула ресниц, фото работы).
3. **Календарь:** день/неделя, создание записи вручную (клиент из базы или новый), перенос drag-and-drop, блокировка времени, перерыв, отпуск.
4. **Клиенты:** список, поиск, карточка, история, заметки, аллергии, формулы, теги, экспорт/удаление по запросу клиента.
5. **Услуги и цены:** редактирование каталога, скрытие услуги, разные цены для мастеров.
6. **Политики и платежи:** окна отмены/переноса, депозиты, возвраты, выплаты.
7. **Команда (салон):** приглашение мастеров по ссылке, назначение услуг, графики, права.
8. **Портфолио и профиль:** загрузка работ, порядок, теги.
9. **Отзывы:** просмотр, ответы (V2).
10. **Статистика:** доход, визиты, no-show, топ услуг, retention.
11. **Уведомления мастеру:** новая запись, отмена, перенос, оплата депозита, отзыв, конфликт.
12. **Настройки/биллинг:** подписка (см. 20, Q6), язык, данные, удаление аккаунта.

## 7. Lash-специфика (то, что делает продукт нишевым)

### 7.1. Услуги (шаблон каталога)

### 7.2. Правило цены коррекции
Цена коррекции зависит от числа дней с последнего наращивания: например, ≤ 14 дней — цена A, 15–21 — цена B, > 21 — как новое наращивание. Пороги настраиваются мастером. Клиент видит правило при записи; система может подставить нужный вариант автоматически по истории.

### 7.3. Lash-профиль клиента
- Формула: тип эффекта, изгиб (например C/CC/D), диаметр, длины по зонам глаза (карта «внутренний угол → внешний»), клей, время выдержки.
- Форма глаз, особенности (нависшее веко, чувствительность).
- Аллергии и реакции на клей/материалы, результат патч-теста (дата).
- Фото до/после (только с согласием).
- Рекомендованный интервал коррекции (по умолчанию 14–21 день).

Это **данные о здоровье** (аллергии, реакции) → особая категория по GDPR, см. раздел 18.

### 7.4. Предвизитные вопросы
Настраиваемые вопросы при записи: носите ли контактные линзы, были ли реакции, есть ли чужое наращивание для снятия, беременность/лактация (по желанию мастера). Ответы хранятся в записи и в профиле клиента.

### 7.5. Послевизитный цикл
Push с уходом (не мочить 24 ч и т.п.), просьба об отзыве через 2–3 часа, напоминание о коррекции за 3–4 дня до окончания окна «дешёвой коррекции».

## 9. Функциональные требования по модулям

### 9.1. Аутентификация и аккаунты

### 9.2. Профиль бизнеса и мастера
- Бизнес (`business`): название, slug (`beautyapp.link/anna-lash`), описание, адрес, координаты, часовой пояс, валюта, язык по умолчанию, контакты, соцсети, политика.

- V2: серия записей («каждые 3 недели, 6 раз») с проверкой доступности всей серии и понятным сообщением, какие даты не прошли.

## 11. Требования к backend API

### 11.1. Принципы
- **Единый backend для iOS, Android и web** [Мы]: клиенты не содержат бизнес-правил календаря и платежей — только UI и валидация первого уровня.

- Реальное время: push + серверные события (SSE/WebSocket) для обновления календаря при изменениях от других устройств.
- Наблюдаемость: структурные логи, трассировка, метрики, алерты; аудит-лог доступа к персональным данным.

## 12. Правила календаря и предотвращения double booking

### 12.1. Расчёт свободных слотов
Слот доступен, если одновременно:
1. Внутри рабочих часов мастера в дату (с учётом `schedule_exception`), в локальной таймзоне бизнеса.
2. Не пересекается с перерывом, `time_off` или блокировкой.
3. Не пересекается с существующей записью в статусах `hold` (не истёк), `pending_payment`, `confirmed`, `checked_in`, `in_progress` — с учётом `block_end_at` (конец + буфер).
4. Соблюдены `min_notice_min` (например, нельзя записаться менее чем за 2 часа) и `max_advance_days`.
5. Начало кратно `booking_step_minutes` (например, каждые 30 или 15 минут).
6. Достаточно непрерывного времени на **всю** длительность (услуга + добавки + буфер).
7. Для коррекции проверено правило `refill_rule` (7.2), если применимо.

Расчёт выполняется **только на сервере**; клиенты получают готовый список слотов. В ответе — таймзона бизнеса и UTC-время.

### 12.2. Защита от double booking (обязательно на уровне БД)
[Мы] Рекомендация для PostgreSQL:
- Расширение `btree_gist` и **exclusion constraint**: по `staff_id` запрещено пересечение диапазонов `tstzrange(start_at, block_end_at)` для записей в «занимающих» статусах.
- Гарантия действует даже при гонке двух одновременных запросов; приложение обрабатывает `exclusion_violation` как `409 slot_unavailable`.
- Ручное «наложение» владельцем (осознанный овербукинг) — флаг `override_overlap = true`, такие записи исключены из ограничения условием `WHERE`.
- **Hold-механика:** при выборе слота создаётся запись `hold` на 10 минут (TTL, `hold_expires_at`) — пока клиент вводит данные и платит; фоновая задача помечает просроченные как `expired`. После успешного платежа `hold → confirmed`.
- Создание и перенос выполняются в транзакции с `SERIALIZABLE`/`SELECT ... FOR UPDATE` по мастеру; повтор запроса с тем же `Idempotency-Key` возвращает тот же результат.
- Перенос drag-and-drop использует `If-Match` (версия): если запись изменили на другом устройстве — конфликт `412`, календарь обновляется.
- Один клиент не может иметь две пересекающиеся записи у разных мастеров без предупреждения (мягкое правило).

### 12.3. Часовые пояса и DST
- Хранение — UTC; отображение — в таймзоне **бизнеса** (не устройства клиента), если клиент в другом поясе — показывается «по времени салона».
- Переход на летнее/зимнее время: несуществующие локальные времена (пропущенный час) не предлагаются; неоднозначные (повторный час) разрешаются по offset.
- Напоминания рассчитываются в UTC от `start_at`, «тихие часы» — в локальном времени получателя.

### 12.4. Дополнительные правила
- Максимум записей клиента в день/неделю (настройка) — защита от злоупотреблений.
- Блокировка в прошлом запрещена, кроме ручного внесения владельцем («записать задним числом»).
- Изменение графика при наличии будущих записей: сервер показывает список конфликтующих записей и предлагает перенести/уведомить клиентов; молча ломать записи запрещено.
- Отмена/перенос с любого устройства сразу отражается у всех (push + события).
- Аудит: каждое изменение записи пишется в `appointment_event`.

## 13. Политика отмены, переноса и no-show

### 13.1. Настройки мастера (на бизнес и на услугу)
- `free_cancellation_hours` — окно бесплатной отмены (например, 24 ч).
- `reschedule_window_hours` — до какого срока клиент сам переносит; максимум переносов на запись (например, 2).
- `late_cancel_rule` — что происходит при поздней отмене: удержать депозит целиком / часть / вернуть.
- `no_show_rule` — при неявке: удержать депозит; (V2) списать сбор с карты в размере N%.
- Автоматически или вручную: мастер может «простить» удержание одним нажатием (как и у Booksy).

### 13.2. Матрица решений (MVP, депозит есть)
| Ситуация | Депозит | Слот |
|---|---|---|
| Клиент отменил ≥ N часов до визита | возврат 100% | освобождается, в V2 предлагается листу ожидания |
| Клиент отменил < N часов | удержание (по правилу) | освобождается |
| Перенос в допустимое окно | сохраняется, привязан к новой дате | новый слот занят, старый свободен |
| Перенос вне окна | как при поздней отмене, либо запрет — по настройке | |
| Мастер отменил | возврат 100% + извинительное сообщение | освобождается |
| No-show | удержание | освобождается, счётчик no-show у клиента (только внутри бизнеса) |
| Ошибочный no-show (клиент оспорил) | мастер может вернуть депозит | статус меняется на `cancelled`, событие в аудите |

### 13.3. Прозрачность
- Политика показывается на профиле, при выборе услуги, на экране подтверждения и в письме.
- Клиент явно принимает политику чекбоксом; версия текста политики сохраняется в `consent`.
- Законодательный контроль (ЕС): потребительские права, сборы должны быть заранее и ясно указаны; согласовать формулировки с юристом (см. 20, Q5).

### 13.4. Защита от злоупотреблений
- Повторные no-show: мастер может потребовать депозит (V2) или отключить самозапись для клиента.
- **Не вести общую чёрную книгу клиентов между бизнесами** — это профилирование и риск GDPR (см. 18).

### 14.1. Каналы и принципы
| Канал | Назначение | Комментарий |

| Место освободилось (V2 лист ожидания) | сразу | push + SMS |
| Маркетинг (V2) | по расписанию, с согласием | email/push |

| Событие | Каналы |
|---|---|

### 14.4. Технические требования
- Токены push привязаны к устройству; при `BadDeviceToken` токен удаляется.

- Пользовательские настройки: по типам событий и каналам; отписка не выключает обязательные транзакционные сообщения о самой записи.
- Локальные уведомления (iOS) — как дополнительная страховка для напоминаний о ближайших визитах (V2).

## 15. Схема оплаты и депозитов

### 15.1. Модель
- Деньги идут от клиента к **мастеру**; платформа не держит средства как банк. [Мы] Рекомендуемый провайдер — **Stripe Connect** (Express-аккаунты мастеров, KYC делает Stripe): в Польше доступны карты, Apple Pay/Google Pay, BLIK и Przelewy24 (доступность методов проверить перед стартом — Q5).
- Платформа может брать комиссию (`application_fee`) или работать по подписке (Q6).
- Остаток за услугу в MVP платится мастеру напрямую на месте (наличные/терминал/BLIK); онлайн-оплата остатка и чаевых — V2; Tap to Pay on iPhone — V3.

### 15.2. Депозит: последовательность (MVP)
1. Клиент выбирает слот → сервер создаёт `appointment` в статусе `hold` (TTL 10–15 мин; для методов с переадресацией, как BLIK, — до 15 мин).
2. Сервер создаёт платёж (PaymentIntent) на сумму депозита, привязанный к аккаунту мастера, с `Idempotency-Key`.
3. Приложение показывает платёжный лист (Apple Pay/карта/BLIK). Проверка 3-D Secure/SCA выполняется провайдером.
4. Источник истины — **webhook** провайдера (`payment_intent.succeeded`), а не ответ приложения. Только после него: `hold → confirmed`, отправка уведомлений.
5. Не оплачено к концу TTL → `expired`, слот освобождается.
6. Дубликаты и повторные вебхуки обрабатываются идемпотентно.

### 15.3. Правила депозита
- Вид: фиксированная сумма или процент от цены варианта; по услуге, либо по умолчанию для бизнеса; может быть отключён.
- Депозит вычитается из итоговой суммы при завершении визита.
- Возврат/удержание — по матрице 13.2. Возврат полный или частичный, инициирует система (правила) или мастер (вручную).
- Спор клиента (chargeback) обрабатывается через провайдера; мастеру приходит уведомление с доказательствами (подтверждение политики, время принятия).
- Комиссии провайдера и платформы прозрачно показываются мастеру в отчёте; клиенту — итоговая сумма.

### 15.4. Card-on-file и сбор за неявку (V2)
- Сохранение карты через SetupIntent с явным согласием и текстом условий; списание вне сессии (off-session) возможно, но банк может потребовать аутентификацию — успех не гарантирован, нужны понятные статусы и повторные попытки.
- Авто-сбор или ручное «простить»; лимиты суммы; уведомление клиенту и квитанция.

### 15.5. Выплаты и бухгалтерия
- Выплаты мастеру — по графику провайдера; экран «Платежи и выплаты» показывает баланс, ожидаемые выплаты, историю.
- Чеки/квитанции клиенту по email. Налоги, фискализация и счета-фактуры — ответственность мастера; для наших подписочных платежей платформа выпускает счета сама. Требования к фискализации в Польше и НДС уточнить у бухгалтера (Q5).

### 15.6. Правила App Store
- Оплата **реальных услуг**, оказываемых вне приложения (запись к мастеру, депозит), допустима не через In-App Purchase (правило о товарах и услугах вне приложения).
- Подписка мастера на **функции самого приложения** обычно должна идти через In-App Purchase — уточнить актуальные правила App Review перед выбором модели монетизации (Q6). Риск отмечен в разделе 22.

## 18. Требования GDPR (ЕС / Польша)

> Это продуктово-технические требования, а не юридическая консультация. Перед запуском нужна проверка юристом по защите данных (Q5). Надзорный орган в Польше — UODO (Prezes Urzędu Ochrony Danych Osobowych); национальное законодательство — ustawa o ochronie danych osobowych, а также ePrivacy-нормы Prawo telekomunikacyjne и ustawa o świadczeniu usług drogą elektroniczną.

### 18.1. Роли по GDPR
| Данные | Контролёр | Обработчик |
|---|---|---|
| Клиентская база мастера (клиенты, записи, заметки, lash-профили) | **Мастер/салон** | **Платформа** (Art. 28) |
| Аккаунт пользователя, вход, устройства, аналитика платформы, маркетплейс-профиль | **Платформа** | — |
| Платежи | платёжный провайдер (самостоятельный контролёр/соконтролёр по своей роли) | |
Следствия: договор обработки данных (DPA) с каждым мастером принимается при регистрации; список субобработчиков публикуется; клиент получает уведомление о том, кто контролёр (Art. 13/14).

### 18.2. Правовые основания
- Запись и исполнение услуги — исполнение договора (Art. 6(1)(b)).
- Напоминания о визите — исполнение договора; не требуют маркетингового согласия.
- Маркетинг (SMS/email/push-акции) — **отдельное согласие** (Art. 6(1)(a) и ePrivacy), по умолчанию выключено.
- Бухгалтерские документы — юридическая обязанность (Art. 6(1)(c)).
- Аналитика/улучшение продукта — законный интерес, минимизация и по возможности без идентификации.

### 18.3. Особые категории данных (Art. 9)
- Аллергии, реакции на материалы, патч-тест, беременность/лактация — **данные о здоровье**.
- Требуется **явное согласие** (Art. 9(2)(a)) на хранение в карточке клиента: отдельный чекбокс, понятный текст, возможность отозвать; без согласия функция «lash-профиль» недоступна, но запись возможна.
- Хранение отдельно от общих данных (отдельные таблицы/шифрование полей), доступ только по ролям, полный аудит.
- Фото «до/после» — отдельное согласие на съёмку и отдельное — на публикацию в портфолио.
- Вероятно потребуется оценка воздействия (DPIA, Art. 35) из-за масштабных данных о здоровье — проверить с юристом.

- Данные и бэкапы в **регионе ЕС**; передача в третьи страны только с гарантиями (SCC/DPF), список субобработчиков открытый.
- Шифрование в транзите (TLS 1.2+) и в покое; шифрование чувствительных полей на уровне приложения.
- Минимизация: не собираем дату рождения, адрес, паспортные данные без нужды; поля опциональны.
- Сроки хранения: неактивный клиент — по настройке мастера (по умолчанию 3 года после последнего визита, затем анонимизация); удалённый аккаунт — 30 дней «мягкого удаления», затем окончательное; логи доступа — 12 месяцев.
- Журнал согласий с версией текста и временем.
- Обработка инцидентов: план реагирования, уведомление UODO в **72 часа**, уведомление затронутых лиц при высоком риске.
- Реестр процессов обработки (Art. 30), назначение ответственного за конфиденциальность/DPO — по необходимости (уточнить).
- Дети: минимальный возраст самостоятельного согласия в Польше — 16 лет; записи несовершеннолетних — через законного представителя; не собираем данные о возрасте пользователя без необходимости.
- Аналитика и рекламные SDK минимальны; App Tracking Transparency не требуется, если нет межприложенческого отслеживания; заполнить **App Privacy** в App Store Connect и Privacy Manifest.
- **Не создавать общую «чёрную книгу» плохих клиентов между бизнесами.**
- Публичные отзывы и фото: указание автора по имени/инициалам с возможностью скрыть.

### 18.6. SMS/email и ePrivacy
- Транзакционные сообщения — допустимы без отдельного согласия; маркетинговые — только с согласием, с простой отпиской (Польша: Prawo telekomunikacyjne, ustawa o świadczeniu usług drogą elektroniczną).
- Хранить отметку «кто, когда, откуда, какой текст» согласия.

## 19. Локализация: PL / EN / RU / UK

### 19.1. Принципы
- Языки интерфейса: **польский (pl), английский (en), русский (ru), украинский (uk)**. Основа/ключи — en; польский — рынок старта.
- Язык по умолчанию — язык системы, если поддерживается; иначе en (для рынка PL — pl). Пользователь может сменить язык внутри приложения.
- iOS: **String Catalogs (`.xcstrings`)**, все тексты без хардкода; `LocalizedStringResource`, форматирование через `FormatStyle`.
- **Множественные числа:** pl, ru, uk имеют формы one/few/many/other (например, «1 запись / 2 записи / 5 записей») — использовать plural variations в каталоге, не склеивать строки.
- Формат даты/времени/валюты — по локали и таймзоне бизнеса (`Date.FormatStyle`, `Currency`), 24-часовой формат по умолчанию для PL/UA/RU.
- Расширяемость строк: русский и польский длиннее английского на 20–40% — вёрстка на Dynamic Type, без фиксированной ширины.
- Тестирование: pseudolocalization, снимки экранов на всех 4 языках, длинные строки, крупный шрифт.

### 19.2. Серверная часть
- `user.locale` и `device.locale`; шаблоны уведомлений — по 4 локалям с fallback en.
- Названия услуг и описания мастера — **введены мастером**: хранятся как `i18n jsonb` (по умолчанию на языке мастера + опциональные переводы); публичная страница показывает язык клиента, если перевод есть, иначе язык мастера.
- Категории и шаблоны lash-услуг (7.1) поставляются нами с переводами на 4 языка.
- Ошибки API: машинные коды + локализованные сообщения на клиенте (не строки сервера).
- Юридические тексты (политика конфиденциальности, условия, DPA) — на pl и en обязательно, ru/uk — по возможности (юридический приоритет у pl/en версии).

### 19.3. Особенности
- Украинский и русский — разные языки, не автопереводить друг из друга; проверка носителями.
- Имена и телефоны: международный формат E.164; клавиатура с выбором страны, по умолчанию +48.
- Порядок «имя/фамилия» и склонения не зашиваем в строки; обращение по имени нейтрально («Привет, Анна» без падежей).

## 21. Архитектура

### 21.1. Общая схема
```
 iOS Customer/Pro (SwiftUI)  ─┐
 Android (Kotlin, V3)         ├──►  API Gateway (REST, OpenAPI v1)
 Web-страница записи          ─┘            │
                                            ▼
                    Backend — модульный монолит
     ┌────────────┬─────────────┬─────────────┬───────────────┐
     │ Identity   │ Catalog     │ Scheduling  │ Booking       │
     │ & Roles    │ & Pricing   │ (slots)     │ (appointments)│
     ├────────────┼─────────────┼─────────────┼───────────────┤
     │ Clients    │ Payments    │ Notifications│ Reviews &    │
     │ (CRM)      │ (Stripe)    │ (outbox)    │ Portfolio     │
     └────────────┴─────────────┴─────────────┴───────────────┘
        │             │               │                │
   PostgreSQL     Stripe          APNs/FCM         Object storage
   (+Redis)       Connect        SMS/Email          + CDN (EU)
```
Фоновые задачи: истечение holds, планирование и отправка напоминаний, пересчёт метрик, очистка данных по срокам хранения, обработка вебхуков.

### 21.2. Принципы, позволяющие подключить Android без переделок
1. **Вся бизнес-логика на сервере:** расчёт слотов, цены, политики, права, платежи. Клиенты — тонкие.
2. **Контракт OpenAPI — единый источник правды;** клиенты генерируются; изменения — только обратно совместимые, breaking → `/v2`.
3. **Платформо-независимые идентификаторы и форматы:** UUID, ISO 8601 UTC, деньги в minor units, E.164, IANA-таймзоны.
4. **Push абстрагирован:** `device.platform` + `push_token`; отправка через слой, который знает APNs и FCM.
5. **Локализация серверных шаблонов** и кодов ошибок — общая для всех платформ.
6. **Feature flags и `min_supported_version`** на сервере.
7. **Единые UX-правила и словарь терминов** (design tokens в JSON) — основа для будущего Android.
8. Платежи через SDK провайдера с общей серверной логикой (webhook — источник истины).
9. Тестовые данные и контрактные тесты общие для всех клиентов.

### 21.3. iOS-приложение (SwiftUI)
- **Xcode 26.6**, Swift 6 (strict concurrency), SwiftUI, минимум iOS 18 (Q4).
- Архитектура: слои **Presentation (SwiftUI Views + `@Observable` ViewModels) → Domain (use cases, модели) → Data (репозитории, API-клиент, кэш)**; навигация через `NavigationStack` + типизированные маршруты и coordinator-подобный роутер.
- Модульность через **Swift Package**: `Core` (сеть, auth, хранилище, логирование), `DesignSystem`, `Localization`, `Features/*` (Booking, Calendar, Clients, Services, Analytics, Payments, Profile, Settings), `SharedModels`.
- Сеть: URLSession + сгенерированный клиент OpenAPI; async/await; авто-refresh токена; retry с backoff; идемпотентные ключи.
- Локальные данные: кэш календаря и клиентов для офлайн-просмотра (SwiftData или GRDB — решить прототипом); токены — Keychain; чувствительные данные — защищённое хранилище, не в открытом кэше.
- Календарь: собственный компонент на SwiftUI (день/неделя, drag-and-drop, сетка времени с шагом 15 мин); realtime-обновления через события сервера.
- Уведомления: UserNotifications + APNs; deep links через **Universal Links** (`/b/{slug}`, `/a/{id}`).
- Платежи: Stripe iOS SDK (PaymentSheet: Apple Pay, карты, BLIK).
- Аналитика и краш-репорты: только необходимое, с согласием (раздел 18).
- Доступность: VoiceOver, Dynamic Type, контраст, Reduce Motion.
- Тестирование: unit (Domain), snapshot (Design System), UI-тесты ключевых сценариев (запись, перенос, отмена), контрактные моки API.
- CI/CD: Xcode Cloud или GitHub Actions + Fastlane, TestFlight, автоматический релизный чек-лист (privacy manifest, локализации).

### 21.4. Backend: доменные правила, живущие только на сервере
Расчёт доступности, exclusion-constraint против пересечений, политики отмены и депозитов, права и изоляция арендаторов, расписание уведомлений, обработка платёжных webhook-ов, retention и анонимизация данных.

## Приложение A. Глоссарий
- **Слот** — свободный интервал начала записи.
- **Hold** — временное удержание слота на время оформления.
- **Buffer / padding** — время после услуги на подготовку/уборку.
- **Refill / коррекция** — поддерживающая процедура через 2–3 недели после наращивания.
- **Deposit** — предоплата, вычитаемая из итоговой суммы.
- **No-show** — неявка клиента без отмены.
- **Card-on-file** — карта, сохранённая для возможного списания сбора.

## Приложение B. Что не входит в MVP (осознанно)
Маркетплейс с поиском по городу, лист ожидания, абонементы и подарочные карты, лояльность, склад, кампании, чат, Android, приём оплаты картой в приложении (Tap to Pay), сети салонов, расширенные роли (Manager/Reception).
